## Plan: Autopilot Feature-Flag Delivery

Add a dedicated feature-flag rollout specialist that both local and cloud autopilot consult during planning, implementation, review, and documentation. The recommended approach is to introduce the agent first as a shared specialist rather than a top-level pipeline stage, then update both pipelines to require explicit rollout plans for user-visible changes, API changes, side effects, and database-affecting work. V1 should support broad rollout planning across UI, code, APIs, side effects, and data-path concerns, while limiting database work to safe expand/contract patterns and documented activation steps rather than destructive runtime switching.

**Steps**
1. Phase 1 — Define rollout contract and triage decision model. Create a repository-wide feature-flag delivery convention that classifies changes into rollout classes: UI/page behavior, controller/service behavior, API behavior, background/side-effecting work, and data/schema changes. At the same time, define triage outputs for rollout status: `rollout-required`, `rollout-optional`, or `rollout-exempt`, with explicit exemption rules for docs-only, test-only, internal refactors with no observable behavior change, build/CI/config cleanup with no runtime effect, and emergency security fixes. Define required plan outputs using a stable checklist artifact: flag name, default state, old-path behavior, new-path behavior, impacted surfaces, activation steps, rollback behavior, telemetry expectations, cleanup strategy, and side-effect behavior when the flag is off. This phase blocks all later work.
2. Phase 1 — Design the new specialist agent. Add a new agent such as `feature-flags.agent.md` under `.github/agents/` with a narrow charter: for issues triage marked `rollout-required` or `rollout-optional`, decide the flag strategy, specify dual-path requirements, identify unsafe areas like schema or side effects, and emit a rollout checklist that downstream agents must follow. This agent should not replace backend/frontend/security/testing/docs; it should guide them.
3. Phase 1 — Adopt real database migration conventions and define flag naming/storage conventions. Replace the current `Program.cs` startup assumption around `db.Database.EnsureCreated()` with an explicit EF Core migrations workflow for `AchievementDbContext`: check in a real baseline migration, document the command path for generating future migrations, and externalize migration execution into a dedicated step instead of relying on web-app startup. The chosen operating model is wrapper-driven externalization: local development uses a wrapper script or task that runs the migration step before app startup, integration tests invoke the same migration path from test setup or fixture code, and cloud delivery uses a separately invoked migration step before activation. The plan must state who invokes each path and what happens when it fails. Schema work uses expand/backfill/switch/contract sequencing, backward-compatible migrations land before flag activation, and destructive cleanup stays in a later cleanup issue. Extend the current runtime model around `Features/FeatureFlags.cs` and `FeatureManagement` configuration so new flags follow one documented naming rule, default off by default, and are representable both in local config and Azure App Configuration. Decide how temporary rollout flags differ from permanent product flags. This phase blocks implementation and docs updates.
4. Phase 2 — Update triage in both pipelines to make the feature-gating call early. Modify local `triage.agent.md` and cloud `cloud-triage.md` so triage explicitly decides whether rollout gating is required, optional, or exempt, records the rationale on the issue, and passes that decision downstream as part of the handoff artifact. `rollout-optional` must mean "not exempt, but the plan agent must explicitly decide whether to ship behind a temporary flag or record why an ungated change is acceptable"; it cannot mean "skip rollout analysis." Review validates the plan artifact was completed, but the plan agent owns the yes/no flagging verdict for optional issues. This phase depends on 1-3 and blocks downstream prompt changes.
5. Phase 2 — Update local planning/orchestration. Modify local autopilot, plan, implement, review, docs, and deliver agent prompts so the local pipeline reads triage’s rollout decision, invokes the new specialist during planning when appropriate, carries the rollout contract into implementation, validates flag-off and flag-on behavior in review, documents verification steps for both states in the standalone docs stage, and creates a cleanup follow-up issue for temporary flags. This phase depends on 1-4.
6. Phase 2 — Update cloud planning/orchestration. Modify `cloud-plan.md`, `cloud-implement.md`, `cloud-review.md`, `cloud-docs.md`, and supporting cloud documentation so the cloud pipeline follows the same rollout contract. The cloud plan stage should embed the feature-flag rollout plan in the issue comment; cloud implement should instruct the Copilot coding agent to preserve old behavior behind a default-off flag and should stop treating docs as part of implement; cloud review should block on missing dual-path validation; cloud docs should publish how to verify both states and emit a human-run activation packet for Azure App Configuration that includes the key, label/environment, target value, prerequisites, validation steps, and rollback steps. The cloud pipeline must never auto-enable flags. This phase depends on 1-4 and can run in parallel with step 5.
7. Phase 2 — Add issue and PR artifact requirements. Update triage, plan, review, docs, and PR-body guidance so every rollout-sensitive change includes a checklist-style rollout artifact with: rollout decision, whether the decision is required or optional, the plan agent's final flagging verdict, flag name when used, default-off state, verification steps for off/on, migration notes if applicable, side-effect gating notes, activation instructions, temporary/permanent flag status, temporary-flag owner, intended cleanup milestone, and cleanup issue reference. If a `rollout-optional` issue deliberately ships without a flag, the plan and review artifacts must say so explicitly and justify it. This phase is parallel with steps 5-6.
8. Phase 3 — Add runtime rollout helpers and conventions in app code. Introduce the minimum shared runtime patterns needed for agents to implement flags consistently: documented use of `[FeatureGate]` for whole-route gating, `IFeatureManager` or `IFeatureManagerSnapshot` checks for behavior branching, Razor/view gating patterns, API branching guidance, side-effect gating guidance, and EF Core migration rollout guidance for expand/backfill/switch/contract. Side-effect guidance must be explicit: when the flag is off, the default expectation is suppression rather than shadow execution, and any exception must be called out in the rollout checklist with idempotency and replay handling. This phase depends on 3 and should remain convention-focused unless helper code is truly needed.
9. Phase 3 — Add verification guidance, telemetry, and tests. Define the repository-level testing contract for flagged work: tests must cover default-off path, flag-on path, route visibility, API compatibility, side-effect suppression when the flag is off, and telemetry/logging that identifies which rollout path executed. For database-affecting work, tests and docs should verify migration safety, backward compatibility, and the externalized migration step itself, including clear failure behavior before flag activation proceeds. Expand/backfill/switch flows must define a lightweight backfill completion gate before switch/activation, such as an explicit row-count or invariant check recorded in docs and referenced in the plan artifact. This phase depends on 5-8.
10. Phase 3 — Add cleanup automation design and ownership. Set cleanup ownership to a hybrid model: review blocks approval if a temporary rollout flag has no cleanup reference, docs records that cleanup issue in its verification output, and merge-stage automation is backstop-only. Local `deliver` and cloud `cloud-finish.yml` should create the cleanup issue only if upstream planning, review, or docs failed to establish it. This step must explicitly cover the cloud finish workflow permissions, issue-creation logic, and idempotency rules. This phase depends on 5-7.
11. Phase 4 — Update repo documentation and examples. Update `AI-SDLC-LOCAL.md`, `AI-SDLC-CLOUD.md`, `README.md`, and `architecture.md` to explain the new feature-flag delivery model, triage’s rollout decision, the standalone docs stage, real migration expectations, how rollout works locally versus in cloud, and the activation/cleanup model. Add at least one end-to-end example showing old behavior with flag off and new behavior with flag on. This phase depends on 5-10.
12. Phase 4 — Validate workflow compilation and local prompt consistency. Because cloud workflow `.md` files change, delete corresponding `.lock.yml` files first and run `gh aw compile`. Validate local prompt references and cloud workflow references both recognize the new specialist, triage’s rollout decision, the standalone docs model, and cleanup issue backstops in `cloud-finish.yml`. This phase depends on 6 and 11.
13. Phase 4 — Execute one pilot issue through both pipelines. Use one representative issue that changes visible behavior plus some server logic and one representative issue with a database migration to validate the contract end to end: triage classifies rollout status, plan emits rollout details, the migration step runs separately from app startup, implement ships dark, review checks both states, docs explains activation, and cleanup issue creation works. The cloud pilot must run through review, docs, migration execution, and finish so the cleanup backstop and migration handoff are actually exercised. This phase depends on 9-12.

**Decisions**
- Include in scope: UI/page behavior, controller/service logic, API behavior, background jobs/side effects, and database rollout planning.
- Database scope: include real EF Core migrations as part of the rollout model, with expand/backfill/switch/contract patterns available to the planner and implementer, and treat migration execution as an externalized operational step rather than a web-app startup responsibility.
- Documentation ownership: docs are a standalone post-review stage only; implement should not own rollout documentation beyond code comments or required PR metadata.
- Cleanup policy: create a follow-up cleanup issue automatically for temporary rollout flags and require that reference in plan/review/docs artifacts.
- Preferred architecture: add a shared specialist agent rather than a new top-level pipeline stage first, so local and cloud can converge on one rollout contract with fewer orchestration changes.
- Triage ownership: triage is the first decision point for rollout status and must classify issues as rollout-required, rollout-optional, or rollout-exempt, with rationale recorded in the issue handoff.
- Optional rollout semantics: `rollout-optional` still requires full rollout analysis. The plan agent makes and records the deliberate yes/no flagging decision instead of silently treating the change as exempt.
- Cloud activation ownership: cloud flag activation is owned by `rbmathis` as the human release operator using Azure App Configuration after docs publishes the activation packet and prerequisites; neither `cloud-docs` nor `cloud-finish.yml` enables the flag.
- Migration execution ownership: schema changes are applied by a dedicated migration step outside normal app startup. Local development uses a wrapper script or task, integration tests use fixture/setup-driven invocation of that same migration path, and cloud uses a separately invoked migration step before activation. The plan must name the operator or automation path for each environment.
- Temporary flag metadata: keep temporary flag metadata lightweight. Every temporary flag must declare only an owner, an intended cleanup milestone, and a cleanup issue reference.
- Side-effect default: when a flag is off, side effects are suppressed by default. Shadow execution or replay behavior must be explicitly justified in the rollout checklist and paired with idempotency handling.
- Canonical artifact shape: the rollout contract uses a checklist format in the plan comment so local and cloud stages validate the same fields consistently.
- Delivery behavior: autopilot ships new work dark by default; enabling the flag remains a deliberate human-controlled action after validation.

**V1 Contract**
- Activation ownership: autopilot never enables flags automatically. Local activation is human-controlled through local configuration, and cloud activation is human-controlled through Azure App Configuration by `rbmathis` as the human release operator after the docs stage publishes the activation packet. That packet must include the App Configuration key, label/environment, intended value, required migration or deployment prerequisites, validation steps, and rollback steps. `cloud-finish.yml` is not an activation step, and migration execution is a separate prerequisite when schema changes exist.
- Exemption policy: triage marks issues `rollout-exempt` when they are docs-only, test-only, internal refactors with no observable behavior change, build/CI/config cleanup with no runtime effect, or emergency security fixes where delayed activation would be inappropriate. Triage marks issues `rollout-optional` when the change is low-risk and user-invisible but may still benefit from a dark launch; those issues still require planner review and an explicit recorded verdict on whether a temporary flag will be used. Triage marks issues `rollout-required` for user-visible behavior, API changes, side effects, risky server logic, and database-affecting changes.
- Cleanup issue mechanics: review blocks approval of temporary rollout flags unless a cleanup issue reference exists. The docs stage records that cleanup issue in the verification comment. Local `deliver` and cloud `finish` are backstops only and create the cleanup issue at merge time only if upstream planning, review, or docs failed to establish that reference.
- Observability: rollout-sensitive implementations must emit enough logging and/or telemetry to identify which path executed, whether the flag was on or off, and any side-effect suppression decisions. Review checks for this explicitly.
- Testing seams: flagged changes must define deterministic flag control for unit and integration tests. Local tests may use configuration overrides or injected feature-manager seams; cloud/runtime documentation must explain Azure App Configuration fallback expectations separately from test setup.
- Canonical rollout artifact: the plan comment is the source of truth. It must always include a checklist-style rollout section containing rollout status, rollout-required/optional/exempt rationale, the plan agent's flagging verdict, flag name, default state, old/new path behavior, impacted surfaces, migration notes, activation steps, rollback steps, observability requirements, side-effect off-state behavior, temporary/permanent status, and cleanup issue reference.
- Temporary flag metadata: every temporary flag checklist entry must include an owner and intended cleanup milestone, but should stay lightweight beyond that.
- Backfill gate: expand/backfill/switch changes must define one lightweight completion check before switch or activation, such as a row-count parity check, null-free invariant, or other explicit data-quality gate recorded in docs.
- Side-effect semantics: off-state means suppression by default. If the plan chooses shadow mode, deferred replay, or another exception, it must document why that is safe and how duplicate execution is prevented.
- Migration conventions: database work uses explicit EF Core migrations with expand/backfill/switch/contract sequencing. The first migration milestone is replacing the current `Program.cs` `EnsureCreated()` path with checked-in migrations for `AchievementDbContext` plus a documented wrapper-driven external migration step for local development, integration tests, and cloud delivery. The web app must not be the primary schema migrator. Local dev and tests may automate the external step for convenience, but they still use the same migration path rather than in-app schema creation. The feature flag gates code-path adoption, not the existence of a backward-compatible schema change. Destructive schema cleanup belongs to a later cleanup issue.

**Feature Agent Personality**
- Agent name: `feature-flags`
- Voice: release engineer / casino pit boss. Calm, watchful, and slightly ominous. Talks like someone managing a high-stakes table where nobody gets to improvise with the bankroll.
- Job framing: rollout plans are "tables," unsafe assumptions are "bad bets," default-off is "keeping the house solvent," and activation is "opening the velvet rope."
- Tone rules: concise, risk-aware, and unsentimental. It should challenge weak rollout ideas directly, especially around database changes, side effects, and API compatibility.
- Required outputs: a rollout verdict, the recommended gating strategy, unsafe areas to avoid, required dual-path tests, observability requirements, migration sequencing notes, activation/rollback guidance, and whether the flag is temporary or permanent.

**Further Considerations**
1. Keep the new specialist named `feature-flags`; it is clearer and easier for contributors to discover than `release-guard`.
2. Prefer temporary rollout flags by default for issue-driven delivery; permanent product flags should be called out explicitly in the plan so cleanup automation does not misfire.
3. Treat rollout decisions as part of issue state, not PR-only metadata, so local and cloud pipelines can stay aligned off the same handoff artifact.
